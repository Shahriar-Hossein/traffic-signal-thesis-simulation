# Adaptive vs. Fixed-Time Traffic Signal Control — A Simulation Study

A Pygame-based microscopic simulation of a four-approach urban intersection, built to compare a
**fixed-time signal controller** against a **queue-responsive (priority) controller** under
saturated demand, and to measure the difference in throughput, delay, and directional equity from
~904,000 logged vehicle crossings.

---

## 1. Core idea

A conventional fixed-time signal gives every approach the same green duration in the same order,
forever, regardless of how many vehicles are actually waiting. When one approach is empty its green
time is still spent, and the intersection pays a fixed startup/clearance penalty on every phase
change.

This project asks a narrow, measurable question:

> If the controller instead **allocates green time in proportion to the queue it can see**, and
> **serves the longest queue first**, how much throughput and delay does that buy at a single
> isolated intersection — and what does it cost in fairness and worst-case waiting?

The contribution is not a new optimisation algorithm; it is a **controlled, high-replication
empirical comparison** of two simple, fully-specified controllers on identical demand, plus an
explanation of *where the measured gain actually comes from*. That last part matters: the analysis
in this repo shows the gain is driven far more by **reduced lost time per cycle** than by the
"intelligence" of the queue-based ordering.

## 2. The scenario

### Intersection

- One isolated, signalised, four-approach intersection (`right`, `down`, `left`, `up`),
  rendered at 1008×1000 px over a city-intersection background.
- **Three lanes per approach**, with a fixed lane-to-movement assignment
  (`config.turnDirections`):

  | Lane | Movement |
  |------|----------|
  | 0 | left turn |
  | 1 | through |
  | 2 | right turn |

- Vehicles in lanes 0 and 2 turn with probability `turnProbability = 0.5`; the rest go straight.
  Measured share of turning vehicles: **33.3%** of all generated traffic.
- Turning is a real trajectory, not a teleport: a cosine/sine arc over 30–60 frames, with the
  trigger point solved analytically so the arc lands in a randomly chosen lane of the receiving
  approach (`Vehicle._compute_trigger_offset`). Turning vehicles physically block followers until
  the turn completes, and post-turn vehicles run a gap check against traffic already in the new
  lane.
- Car-following is a simple gap constraint (`movingGap = 15 px` moving, `stoppingGap = 15 px`
  queued). No lane changing.

### Demand

- Vehicles are generated by a dedicated thread at a **measured 5.00 veh/s = 300 veh/min =
  18,000 veh/h** total ([core/generator.py](core/generator.py) sleeps 1 s every 5 vehicles).
- Traffic mode `even`: each approach receives **25%** of arrivals (uniform).
- Four vehicle classes, uniformly sampled, with different free-flow speeds:

  | Class | Speed (px/frame) |
  |-------|------------------|
  | bike | 2.25 |
  | car | 2.00 |
  | bus | 1.75 |
  | truck | 1.50 |

### Operating regime — this is important

Demand (18,000 veh/h) is far above what the intersection can discharge (**~9,900 veh/h** under
fixed-time, **~11,400 veh/h** under priority). The volume-to-capacity ratio is therefore
**v/c ≈ 1.8 (fixed) and ≈ 1.6 (priority)**.

The intersection is **permanently oversaturated**: queues never clear, and mean delay grows
monotonically through every run (second-half mean wait is **2.1×–2.9×** the first-half mean).

Consequence for interpretation: in this regime **throughput is the primary performance measure**
and delay is a secondary, run-length-dependent measure. Absolute delay numbers are only comparable
between algorithms *at the same run duration* — they are not a property of the algorithm alone.
A claim of the form "algorithm X gives a 190 s average delay" is meaningless here; only
"algorithm X gives 19% less delay than Y over the same 20-minute run" is defensible.

The `uneven_mode` machinery (`up`, `down`, `left`, `right`, `up_down`, `left_right`, `right_down`,
`left_up`, …) supports directionally biased demand, but **the retained dataset contains only the
`even` mode**. See §9.

## 3. The algorithms

Both controllers run in a background thread, drive `state.currentGreen` / `state.currentYellow`,
and begin with a **10-second all-red warm-up** so an initial queue accumulates before the first
green. Yellow is fixed at **5 s** for both. This makes the comparison a clean single-variable
contrast: only the green allocation and the phase ordering differ.

### 3.1 Baseline — Fixed-time control ([core/cycle_fixed.py](core/cycle_fixed.py))

```
loop forever:
    for approach in [right, down, left, up]:      # fixed order
        green(approach, 12 s)                     # fixed duration
        yellow(approach, 5 s)
```

- Phase = 12 s green + 5 s yellow = **17 s**; cycle = **68 s**; measured phase interval
  17.0 s (min 17, max 18) — the implementation is essentially exact.
- Nothing about vehicle presence enters the decision. It is a pure open-loop controller.
- This is the standard reference case in the signal-control literature and the correct baseline
  for a "does adaptivity help?" question.

### 3.2 Proposed — Queue-priority control ([core/cycle_priority.py](core/cycle_priority.py))

```
loop forever:                                       # one "round"
    order ← the 4 approaches sorted by weighted queue, descending
    while order not empty:
        a ← order.pop_front()                       # serve the largest queue first
        W ← weighted_queue(a)
        g ← clamp(⌊0.75 · W⌋, 6, 24)                # demand-proportional green
        green(a, g), aborting early if raw_queue(a) ≤ 3 and elapsed ≥ 6 s
        yellow(a, 5 s)
        order ← re-sort remaining approaches by their current weighted queue
```

Three mechanisms are at work:

1. **Demand-proportional green** — green time scales linearly with the queue, clamped to
   `[6 s, 24 s]`.
2. **Priority ordering** — within each round, the approach with the largest queue is served next.
   Because approaches are *popped* from the round, **every approach is served exactly once per
   round**. This bounds starvation: an approach can wait at most two rounds (≈7 phases) between
   greens. It is a "largest-queue-first within a round-robin envelope" policy, not pure greedy
   largest-queue-first.
3. **Early termination** — green ends as soon as ≤3 vehicles remain, subject to a 6 s minimum, so
   the controller does not hold green over an empty approach.

**Queue weighting** (`utils/counters.get_weighted_vehicle_counts`) counts only *uncrossed* vehicles
and weights each by `1 / speed`, so slower vehicles count more:

| Class | speed | weight = 1/speed |
|-------|-------|------------------|
| truck | 1.50 | 0.667 |
| bus | 1.75 | 0.571 |
| car | 2.00 | 0.500 |
| bike | 2.25 | 0.444 |

> ⚠️ **Discrepancy to report honestly in the thesis.** [utils/counters.py](utils/counters.py) also
> defines a PCU-style table `VEHICLE_WEIGHTS = {car: 1.0, bike: 0.5, truck: 2.0, bus: 2.5}` — but
> it is **never used**. The weights actually applied are the `1/speed` values above. So the
> effective weighting is much flatter than a passenger-car-equivalent scheme (a truck counts 1.5×
> a bike, not 4×). Either describe the `1/speed` scheme as the method, or wire up
> `VEHICLE_WEIGHTS` and re-run. Do not describe the PCU table as the method.

### 3.3 Variant — Fairness-priority ([core/cycle_fairness_priority.py](core/cycle_fairness_priority.py))

Same skeleton, three parameter/logic changes:

| | `cycle_priority` | `cycle_fairness_priority` |
|---|---|---|
| Order within a round | re-sorted after **every** phase | fixed at the **start** of the round |
| Green formula | `⌊0.75·W⌋` | `⌊0.67·W⌋` |
| Green cap | 24 s | 18 s |
| Early exit | raw queue ≤ 3 | **every lane** ≤ 1 vehicle |

Both variants serve each approach once per round, so "fairness" here really refers to the
**shorter green cap** (18 s) — which limits how much one heavy approach can monopolise the
cycle — rather than to a different service guarantee.

**There is no retained data for this variant.** It is implemented and selectable but was not part
of the measured comparison. Present it as an implemented-but-unevaluated extension, or run it
before submission.

## 4. Experimental design (methodology)

| Item | Setting |
|------|---------|
| Independent variable | Controller (`fixed` vs `priority`) |
| Control variables | Demand 5 veh/s, `even` split, turn probability 0.5, 5 s yellow, 10 s warm-up, identical geometry/vehicle mix |
| Run durations | 300 s, 600 s, 1200 s, 1800 s (a run-length sweep, not a time series) |
| Replications | 150 / 80 / 30 / 15 runs **per controller** at 300/600/1200/1800 s |
| Randomisation | Independent RNG streams per run: vehicle class, approach, lane, turn decision, target lane |
| Execution | 5 concurrent instances per batch via `run_simulation.py`; controller fixed per batch |
| Primary metric | **Throughput** — vehicles discharged per run (one log row per stop-line crossing) |
| Secondary metrics | Mean / median / p90 / p95 / max **stopped delay** per vehicle |
| Equity metrics | Per-approach mean delay: max–min spread, standard deviation, Jain's fairness index |
| Signal metrics | Phase interval, cycle length, per-approach green share, service gap between consecutive greens of the same approach |

**Delay definition.** Each `Vehicle` accumulates wall-clock seconds during which it was blocked
from moving, from any cause — red signal *or* the vehicle in front
([models/vehicle.py](models/vehicle.py), "wait time tracking"). It is therefore **total stopped
delay**, not control delay attributable to the signal alone. The value is written to CSV at the
instant the vehicle crosses its stop line.

**Timing model.** The simulation is **wall-clock driven** (`time.sleep(1)` in the controller
threads, renderer capped at 60 FPS), not discrete-event. It is a real-time simulator, so results
carry a dependence on machine load. See §9.

### Data quality issues — check these before writing the thesis

1. **`vehicle_id` is not a unique identifier.** `utils/logger.log_vehicle` writes `id(vehicle)`, a
   CPython memory address that is **reused** after a vehicle is garbage-collected. In the 1800 s
   fixed arm this collapses 73,999 records into 51,929 distinct "ids". **Never report
   `unique_vehicles` from [analyzers/analyze_log.py](analyzers/analyze_log.py)** — it is an
   artefact. Row count is the correct throughput measure. Fix: use a monotonic counter.
2. **Right-censoring of delay.** Only vehicles that *cross* are logged. Vehicles still queued when
   the run ends — the longest-waiting ones — are never recorded. Mean delay is therefore biased
   downward for both controllers, and **more strongly for fixed-time**, which leaves a larger
   residual queue. The reported priority advantage in delay is consequently **conservative**. State
   this explicitly; it is a strength of the argument, not a weakness.
3. **4 corrupted signal logs** (null-padded, `data/log_signals/even/1800/fixed_log_1800_20260623_2209*_signal.csv`)
   from interrupted writes. Excluded from all signal analysis.
4. **35 orphan signal logs** in `even/1800` and 10 in `even/300` with no matching vehicle log
   (aborted runs whose vehicle logs were deleted). Signal analysis is restricted to runs where both
   files exist.
5. The 300 s batch spans a code change (`fix: cpu high consumption`, 2026-05-14). Both arms appear
   on all three collection days and per-day results are near-identical (§6.5), so this does not
   affect the conclusion.

## 6. Results

All numbers below are computed from the logs in `data/`. Percentages are priority relative to
fixed; negative delay = better, positive throughput = better.

### 6.1 Headline: throughput and delay

| Duration | Runs/arm | Throughput fixed | Throughput priority | Δ | Mean delay fixed | Mean delay priority | Δ |
|---|---|---|---|---|---|---|---|
| 300 s | 150 | 787 veh | 885 veh | **+12.4%** | 65.9 s | 58.3 s | **−11.5%** |
| 600 s | 80 | 1,638 veh | 1,861 veh | **+13.6%** | 122.6 s | 102.7 s | **−16.2%** |
| 1200 s | 30 | 3,317 veh | 3,804 veh | **+14.7%** | 233.9 s | 189.8 s | **−18.9%** |
| 1800 s | 15 | 4,933 veh | 5,723 veh | **+16.0%** | 342.4 s | 276.2 s | **−19.4%** |

Discharge rate: fixed is flat at **164–166 veh/min** (~9,900 veh/h) at every duration — exactly what
an open-loop controller should do. Priority rises from **177 veh/min** (300 s) to **191 veh/min**
(1800 s) as queues build to the point where its green allocation saturates at the cap.

**The advantage grows with run length** in both metrics. This is the signature of a capacity
difference compounding in an oversaturated system.

### 6.2 Tail delay

| Duration | p90 fixed → priority | p95 fixed → priority | max fixed → priority |
|---|---|---|---|
| 300 s | 112.2 → 99.6 s (−11.3%) | 120.7 → 111.8 s (−7.4%) | 152.1 → 144.3 s (−5.1%) |
| 600 s | 214.4 → 179.8 s (−16.1%) | 229.2 → 193.4 s (−15.6%) | 277.9 → 245.1 s (−11.8%) |
| 1200 s | 409.7 → 329.6 s (−19.6%) | 439.4 → 358.4 s (−18.4%) | 521.4 → 442.9 s (−15.0%) |
| 1800 s | 614.9 → 485.9 s (−21.0%) | 657.2 → 521.7 s (−20.6%) | 783.3 → 632.1 s (−19.3%) |

Priority improves the **tail as well as the mean** — it is not trading worst-case delay for average
delay. This is the answer to the obvious reviewer objection against priority schemes.

### 6.3 Directional equity

Per-approach mean delay, averaged over runs:

| Duration | Algo | right | down | left | up | **spread** | sd | Jain |
|---|---|---|---|---|---|---|---|---|
| 300 s | fixed | 66.9 | 55.9 | 63.7 | 76.9 | **21.1 s** | 7.55 | 0.9870 |
| 300 s | priority | 57.6 | 58.4 | 58.2 | 58.6 | **1.0 s** | 0.36 | 1.0000 |
| 600 s | fixed | 118.6 | 117.7 | 126.1 | 128.1 | **10.4 s** | 4.52 | 0.9986 |
| 600 s | priority | 102.8 | 102.7 | 103.3 | 101.3 | **2.0 s** | 0.75 | 0.9999 |
| 1200 s | fixed | 232.9 | 231.5 | 227.9 | 243.5 | **15.6 s** | 5.81 | 0.9994 |
| 1200 s | priority | 186.7 | 190.4 | 187.9 | 193.6 | **6.9 s** | 2.65 | 0.9998 |
| 1800 s | fixed | 344.5 | 327.9 | 344.7 | 352.6 | **24.6 s** | 8.98 | 0.9993 |
| 1800 s | priority | 274.9 | 274.7 | 276.9 | 277.9 | **3.2 s** | 1.33 | 1.0000 |

The priority controller is **3×–21× more even across approaches**. This is counter-intuitive and
worth foregrounding: a controller that *deliberately prioritises* one approach produces *more*
equal outcomes than one that treats all approaches identically. The reason is that fixed-time is
only fair in *input* (equal green), not in *output*. Any random imbalance in arrivals persists,
because fixed-time has no mechanism to correct it. The priority controller closes that loop, so
under symmetric demand it equalises the *queues* rather than the *green time*.

### 6.4 Signal behaviour — and why priority actually wins

| Duration | Algo | Phase interval | Cycle | Green/cycle | Lost time/cycle | **Lost time %** | Cycles/h |
|---|---|---|---|---|---|---|---|
| 1200 s | fixed | 17.0 s | 68.1 s | 48.1 s | 20 s | **29.4%** | 52.9 |
| 1200 s | priority | 28.2 s | 112.8 s | 92.8 s | 20 s | **17.7%** | 31.9 |
| 1800 s | fixed | 17.0 s | 68.2 s | 48.2 s | 20 s | **29.3%** | 52.8 |
| 1800 s | priority | 28.5 s | 113.9 s | 93.9 s | 20 s | **17.6%** | 31.6 |

Now the critical diagnostic — **how often does the adaptive controller actually adapt?**

| Duration | Phases at min (6 s) | Phases in between | **Phases at cap (24 s)** |
|---|---|---|---|
| 300 s | 8.8% | 18.6% | **72.6%** |
| 600 s | 4.6% | 9.8% | **85.7%** |
| 1200 s | 2.2% | 4.9% | **92.9%** |
| 1800 s | 1.6% | 3.3% | **95.1%** |

**Under saturated demand the priority controller spends 73–95% of its phases pinned at the 24 s
green cap.** Its green-allocation rule is almost never the binding constraint — the *cap* is. So
functionally it degenerates into a fixed-time controller with a 24 s green and a 113 s cycle,
plus adaptive ordering.

This yields a falsifiable mechanistic explanation. Reducing lost time from 29.4% to 17.7% of the
cycle should raise capacity by `(1−0.177)/(1−0.294) − 1`:

| Duration | Predicted gain from lost-time reduction | **Observed throughput gain** |
|---|---|---|
| 300 s | +14.1% | +12.4% |
| 600 s | +15.7% | +13.6% |
| 1200 s | +16.5% | +14.7% |
| 1800 s | +16.7% | +16.0% |

The prediction tracks observation within 1–2 percentage points at every duration. **The throughput
gain is almost entirely explained by fewer lost-time intervals per hour, not by intelligent
allocation.** Reporting this is the difference between a descriptive thesis and an explanatory one
— and it is the honest reading of the data.

The queue-based *ordering*, meanwhile, is genuinely active: only **26.6%** of priority phase
transitions follow the fixed round-robin successor (vs. 100% for fixed-time), so the controller
reorders constantly. That reordering is what produces the equity result in §6.3, even though it
contributes little to throughput.

**Cost of reordering — service gaps** (time between two consecutive greens of the same approach):

| Algo | mean | p50 | p90 | p99 | max | share > 120 s |
|---|---|---|---|---|---|---|
| fixed (1800 s) | 68.2 s | 68 | 69 | 69 | **69 s** | 0.00% |
| priority (1800 s) | 115.1 s | 116 | 137 | 150 | **204 s** | 10.16% |

Fixed-time guarantees a green every 69 s, always. Priority's guarantee is much weaker: typically
116 s, up to **204 s** in the worst observed case. The bound is structural (at most two rounds),
not accidental, but it is 3× looser than the baseline's. This is the real, quantified cost of the
adaptive policy, and it is what a fairness- or driver-experience-oriented critique would attack.

### 6.5 Robustness

- **Run-to-run variability is tiny**: throughput CV is 0.3–0.9% for both controllers.
- **Delay by vehicle class** shows a consistent ordering under both controllers
  (bike > car > bus > truck), with priority uniformly lower — e.g. at 1800 s, bike 352.5→287.3 s,
  truck 330.4→262.7 s. The gap is a car-following artefact (faster vehicles catch up to and queue
  behind slower ones), not a signal effect, and it behaves identically under both controllers.
- **Cross-day replication** at 300 s (both arms present on three separate collection days):

  | Day | Throughput Δ | Mean delay Δ |
  |---|---|---|
  | 2026-05-14 | +12.6% | −11.9% |
  | 2026-05-15 | +12.4% | −11.8% |
  | 2026-06-19 | +12.1% | −11.5% |

- **Statistical significance**: Welch's t on per-run mean delay gives |t| = 57–108 (n = 15–150 per
  arm), p ≪ 0.001 everywhere. Say this once and move on — with cheap simulation replicates,
  significance is guaranteed and uninformative. **Report effect sizes**, which are large by any
  standard (Cohen's d ≈ 5–7).

## 7. Strengths and weaknesses

### Fixed-time control

**Strengths**
- Deterministic and perfectly predictable: green every 69 s, no exceptions. Strong worst-case
  guarantee, and drivers can learn it.
- Zero sensing requirement — no detectors, no detector failure mode, no cost.
- Cannot be gamed or destabilised by unusual arrival patterns; trivially verifiable and certifiable.
- Genuinely competitive when demand is symmetric and light, where its only inefficiency is idle
  green.

**Weaknesses**
- Green allocation is completely decoupled from demand; idle green on an empty approach cannot be
  reclaimed.
- Short cycle (68 s) means **29.4% of all time is lost time**. Under saturation this is the
  dominant inefficiency.
- Fair in input but not in output: random arrival imbalance persists as delay imbalance
  (spread up to 24.6 s across approaches).
- Static — cannot respond to incidents, surges, or time-of-day variation without manual retiming.

### Queue-priority control

**Strengths**
- **+12% to +16% throughput** and **−11% to −19% mean delay**, with the advantage growing with
  run length.
- Improves the **tail** (p90/p95/max) as well as the mean — no mean-vs-tail trade-off.
- **Dramatically better directional equity** (spread 24.6 s → 3.2 s at 1800 s; Jain ≈ 1.0000).
- Bounded starvation by construction: each approach is served exactly once per round, so the wait
  is capped at ~2 rounds. This is a *provable* property, not an empirical one — worth stating as
  such.
- Degrades gracefully: with the 6 s floor and 24 s cap it can never produce a pathological phase.
- Reclaims idle green through early termination, so it should widen its advantage further under
  asymmetric demand.

**Weaknesses**
- **Its adaptivity is largely inactive in the tested regime** — 73–95% of phases hit the green cap.
  The measured gain is mostly a longer-cycle / lower-lost-time effect that a *retimed fixed-time
  controller with a 24 s green would also capture*. This is the strongest available criticism of
  the result and must be addressed head-on (see §9).
- Weaker worst-case guarantee: max service gap 204 s vs. 69 s; 10% of gaps exceed 120 s. Long,
  variable red is a real driver-experience and red-light-running risk.
- Unpredictable to drivers and to coordinated arterials — this controller cannot participate in a
  green wave.
- Requires complete, accurate real-time queue measurement on all approaches; the study assumes
  perfect sensing with zero latency and zero error.
- Two magic constants (`0.75`, cap `24`) are unjustified and untuned; the cap in particular
  determines the entire result.
- The vehicle weighting actually applied (`1/speed`) is not the documented PCU scheme (§3.2).

## 8. Draft text for the thesis

Adapt freely — these are scaffolds with the numbers already in place, not finished prose.

### Abstract

> Fixed-time signal control allocates green time independently of actual demand, wasting capacity
> at intersections with fluctuating arrivals. This work presents a microscopic simulation study
> comparing a conventional fixed-time controller against a queue-responsive priority controller at
> an isolated four-approach intersection with three lanes per approach and turning movements. The
> priority controller serves approaches in descending order of a speed-weighted queue count and
> allocates green time proportional to that queue, bounded to [6 s, 24 s], while guaranteeing each
> approach exactly one service per round. Both controllers were evaluated over 550 simulation runs
> (≈86 simulated hours, 904,170 logged vehicle crossings) at four run lengths under saturated,
> directionally uniform demand of 18,000 veh/h. The priority controller increased throughput by
> 12.4%–16.0% and reduced mean stopped delay by 11.5%–19.4%, with the advantage increasing with
> run length; 90th-percentile and maximum delay improved by comparable margins. Directional equity
> improved substantially, with the spread in per-approach mean delay falling from 24.6 s to 3.2 s
> over 30-minute runs. Phase-level analysis shows the throughput gain is attributable primarily to
> a reduction in lost time from 29.4% to 17.7% of cycle length rather than to demand-responsive
> allocation per se: under saturation the controller reached its green-time cap in 73%–95% of
> phases. The improvement in equity, by contrast, derives directly from the adaptive phase
> ordering. The adaptive policy's cost is a weaker service guarantee, with the maximum interval
> between successive greens on an approach rising from 69 s to 204 s.

### Methodology

> **Simulation environment.** A microscopic, agent-based simulator was implemented in Python using
> Pygame. The test-bed is an isolated signalised intersection with four approaches and three lanes
> per approach, assigned to left-turn, through, and right-turn movements respectively. Vehicles in
> turning lanes execute a turn with probability 0.5, following a parametric arc into a randomly
> selected receiving lane; the remainder proceed straight. Measured over the generated stream,
> 33.3% of vehicles turn. Car-following is modelled as a minimum-gap constraint of 15 px with no
> lane changing. Four vehicle classes (bike, car, bus, truck) are sampled uniformly with free-flow
> speeds of 2.25, 2.00, 1.75 and 1.50 px/frame.
>
> **Demand.** Vehicles are generated at a measured 5.00 veh/s (18,000 veh/h), distributed uniformly
> across the four approaches and three lanes. This exceeds the discharge capacity of both
> controllers, placing the intersection in a persistently oversaturated regime (v/c ≈ 1.6–1.8) in
> which queues do not clear. Throughput is therefore adopted as the primary performance measure and
> delay as a secondary, run-length-dependent measure.
>
> **Controllers.** [Describe the two controllers per §3, including the 10 s all-red warm-up, the
> fixed 5 s yellow common to both, the 12 s fixed green baseline, and the priority controller's
> weighting, green formula, clamping, early-termination rule, and one-service-per-round guarantee.]
>
> **Experimental design.** A two-arm design with controller as the sole independent variable; all
> geometric, demand and timing parameters were held constant. Each arm was replicated 150, 80, 30
> and 15 times at run lengths of 300 s, 600 s, 1200 s and 1800 s, yielding 275 runs per arm.
> Randomisation across vehicle class, approach, lane, turn decision and receiving lane was
> independent per run.
>
> **Measurement.** Two event logs were written per run: a crossing log recording, for each vehicle
> at the moment it crosses the stop line, its class, approach, and accumulated stopped delay; and a
> signal log recording every green onset with its approach. Stopped delay accumulates wall-clock
> time during which a vehicle is blocked, whether by signal or by the vehicle ahead, and therefore
> represents total stopped delay rather than signal-attributable control delay. Throughput was
> measured as the number of crossing records per run. Equity was quantified by the range, standard
> deviation, and Jain's fairness index of per-approach mean delay. Signal behaviour was
> characterised by phase interval, cycle length, per-approach green share, and the interval between
> successive greens on the same approach. Because delay is recorded only on crossing, vehicles
> still queued at run end are absent from the data; this censoring biases mean delay downward for
> both arms and more strongly for the fixed-time arm, rendering the reported delay advantage
> conservative.

### Results

> [Insert tables from §6.1–6.4.] Across all four run lengths the priority controller discharged
> more vehicles and produced lower delay than the fixed-time baseline. Throughput improved by
> 12.4% at 300 s, rising monotonically to 16.0% at 1800 s, while mean stopped delay fell by 11.5%
> and 19.4% respectively. The fixed-time controller's discharge rate was constant at 164–166
> veh/min across all run lengths, consistent with its open-loop design, whereas the priority
> controller's rose from 177 to 191 veh/min as queues developed. Improvements were not confined to
> the mean: 90th-percentile delay fell by 11.3%–21.0% and maximum observed delay by 5.1%–19.3%,
> indicating that the adaptive policy did not trade worst-case for average performance.
> Run-to-run variability was low (throughput CV 0.3%–0.9%) and results replicated to within 0.5
> percentage points across three independent collection days.
>
> Directional equity improved markedly. Under fixed-time control the spread in mean delay across
> the four approaches reached 24.6 s over 30-minute runs, whereas under priority control it was
> 3.2 s, with Jain's fairness index rising from 0.9993 to 1.0000. Since demand was directionally
> uniform, this indicates that equal green allocation does not produce equal outcomes: stochastic
> imbalance in arrivals persists under an open-loop controller, whereas the priority controller's
> feedback corrects it.
>
> Phase-level analysis identifies the source of the throughput gain. The fixed-time controller
> operated a 68.1 s cycle in which 20 s — 29.4% — was yellow-interval lost time. The priority
> controller's cycle averaged 113.9 s with the same 20 s lost, reducing lost time to 17.6%. The
> capacity gain predicted from this reduction alone is +14.1% to +16.7%, which brackets the
> observed +12.4% to +16.0% at every run length. Consistent with this, the priority controller
> reached its 24 s green-time cap in 72.6% of phases at 300 s, rising to 95.1% at 1800 s: under
> saturation its demand-proportional allocation was rarely the binding constraint. The
> demand-responsive *ordering*, however, remained fully active — only 26.6% of phase transitions
> followed the round-robin successor — and accounts for the equity improvement. The cost of this
> reordering is a weaker service guarantee: the interval between successive greens on an approach
> rose from a tightly bounded 68–69 s under fixed-time to a mean of 115.1 s with a maximum of
> 204 s, with 10.2% of intervals exceeding 120 s.

## 9. Limitations and threats to validity

State these; a thesis that names its own limitations is stronger than one that waits to be told.

1. **The cap confound (most important).** Because the priority controller is capped-out 73–95% of
   the time, this study does not cleanly isolate "adaptive vs. fixed" — it partly compares a 68 s
   cycle against a 114 s cycle. **The single most valuable additional experiment is a fixed-time
   arm with a 24 s green (cycle ≈ 116 s)**, matching the priority controller's cycle length. If
   priority still wins, the adaptivity claim is established. If it does not, the honest finding is
   that the baseline was simply under-timed — still a publishable result, and a far more
   interesting one than an unexamined win. Running this is a few hours of compute.
2. **Only symmetric demand was evaluated.** All retained data is `uneven_mode = 'even'`. The
   priority controller's central theoretical advantage — reallocating green under *asymmetric*
   demand — is therefore **untested**. The generator already supports eight biased modes; running
   `up` (85%/5%/5%/5%) and `left_right` would test exactly the case the design targets and should
   show a much larger gain.
3. **Permanent oversaturation.** v/c ≈ 1.6–1.8 throughout. No undersaturated or near-capacity
   regime was tested, yet that is where most real intersections operate and where adaptive control
   is usually claimed to help most. Delay figures grow with run length and are not steady-state.
4. **Wall-clock timing.** The simulator is real-time, not discrete-event, and batches ran 5
   concurrent instances. Frame rate depends on machine load, so vehicle motion and signal timing
   could in principle drift apart under CPU pressure. Runs of the two controllers were executed in
   separate batches, so this confound is not shared within a batch. The cross-day replication in
   §6.5 (agreement within 0.5 pp) is the evidence against it mattering — cite that, and consider a
   deterministic frame-step mode for future work.
5. **Perfect sensing assumed.** Queue counts are read directly from simulator state: no detector
   error, occlusion, latency, or failure. Real adaptive control degrades under all of these.
6. **Unvalidated traffic model.** Saturation headway, acceleration, startup lost time, and turn
   dynamics are not calibrated to any field data or standard (e.g. HCM). Speeds are in px/frame
   with no stated px-to-metre conversion, so absolute values are not physically interpretable —
   only relative comparisons are. Do not report delay in seconds as if field-comparable.
7. **Isolated intersection.** No network effects, no upstream platooning, no coordination. The
   priority controller's irregular cycle would be actively harmful in a coordinated arterial.
8. **Untuned constants.** `0.75`, the 24 s cap, the 6 s floor, and the ≤3-vehicle early-exit
   threshold were not swept. A sensitivity analysis on the cap alone would strengthen the work
   considerably, and it is cheap.
9. **`vehicle_id` collisions and delay censoring** — see §5.
10. **The `fairness_priority` variant is unevaluated.**

### Suggested next experiments, in order of value

1. Fixed-time arm with 24 s green (matched cycle length) — resolves limitation 1.
2. Asymmetric demand (`up`, `left_right`) for both controllers — resolves limitation 2.
3. Undersaturated demand (1–2 veh/s) — resolves limitation 3.
4. Sensitivity sweep on the green cap (12/18/24/30 s).
5. Run the `fairness_priority` variant as a third arm.

## 11. Running it

### Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install pygame          # the only external dependency
```

Requires Python 3.9+ and a display; the simulator is graphical, not headless.

### Configure a run

Everything is set in [state.py](state.py):

```python
currentMode = "fixed"        # "fixed" | "priority" | "fairness_priority"
uneven_mode = 'even'         # 'even' | 'up' | 'down' | 'left' | 'right'
                             # | 'up_down' | 'left_right'
                             # | 'right_down' | 'right_up' | 'down_left' | 'left_up'
run_mode    = 'time'         # 'time' | 'vehicles'  — how the run ends
duration    = 1200           # seconds          (used when run_mode == 'time')
target_vehicle_count = 500   # vehicles         (used when run_mode == 'vehicles')
count_mode_timeout   = 1800  # seconds, safety cap for 'vehicles' mode
```

Arrival rates are in [config.py](config.py) (`trafficConditions`, `trafficConditionInterval`) — the
generator switches between high/medium/low every 2 minutes. Signal timing defaults are also in
[config.py](config.py) (`defaultGreen`, `defaultYellow`).

#### The two run modes

| | `run_mode = 'time'` | `run_mode = 'vehicles'` |
|---|---|---|
| Ends when | the clock reaches `duration` | all `target_vehicle_count` vehicles have crossed the stop line |
| Fixed quantity | run length | vehicle count |
| Measured quantity | how many crossed | how long it took (`duration_sec` in the sidecar) |
| Log tree | `data/logs/`, `data/log_signals/` | `data/logs_by_count/`, `data/log_signals_by_count/` |

The two modes write to completely separate trees and never touch each other's data or summaries.

Use **`vehicles`** when you want a complete sample: a time run stops the clock mid-stream, so
every vehicle still queued at that moment has no row in the CSV — and those are exactly the
longest-waiting ones, which biases mean wait downward by a different amount for each controller.
A count run logs every vehicle it generates.

Two things to know about count mode: run length becomes an output rather than an input (it varies
with the random high/medium/low sequence drawn), and the tail of the run drains under zero
arrivals, which no time run experiences. Do not pool the two.

### Run

```bash
python3 main.py              # single instance
python3 run_simulation.py    # batch of 5 concurrent instances
```

Logs are written automatically:

- **time mode** → `data/logs/<uneven_mode>/<duration>/<controller>_log_<duration>_<ts>.csv`
- **count mode** → `data/logs_by_count/<uneven_mode>/<N>/<controller>_countlog_<N>_<ts>.csv`,
  plus a `_meta.json` sidecar per run holding the target, the actual counts, `duration_sec`, and
  `stop_reason` (`target_reached` | `timeout` | `user_quit`)

with the matching signal logs under `data/log_signals/` and `data/log_signals_by_count/`.

**Both arms must be run separately** — `currentMode` is a module-level constant, so every instance
in a batch uses the same controller. A count run that hits `count_mode_timeout` is recorded with
`stop_reason: "timeout"` and is excluded from the pooled statistics by the analyzer — it is a
truncated run, not a complete one.

### Analyse

```bash
python3 analyzers/analyze_log.py           # time runs  → data/summary_logs/simulation_summary.csv
python3 analyzers/analyze_count_log.py     # count runs → data/summary_count_logs/count_simulation_summary.csv
python3 analyzers/analyze_signal_log.py    # → data/summary_signals/
python3 analyzers/analyze_first_n_vehicles.py
python3 analyzers/analyze_first_n_vehicles_by_direction.py
```

`analyze_count_log.py` reports `average_duration_sec` and
`average_throughput_vehicles_per_sec` — with the vehicle count fixed, a shorter run is the
result. It also warns whenever a file's row count does not match its vehicle target.

Architecture reference: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Remember: ignore the `unique_vehicles` column (§5.1).
